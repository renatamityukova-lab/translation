# Проект «Transtalion» — постановка задачи

## 1. Суть задачи

Пользователь вводит идентификатор в стиле 1С — фразу на русском языке без пробелов,
записанную в `CamelCase` (каждое слово с большой буквы, слитно).

Пример входа:

```
ДоговорыКонтрагентов
```

Программа должна перевести такой идентификатор на английский язык и выдать результат
в формате, принятом для именования объектов в учётных системах.

Пример выхода:

```
partner_contract
```

## 2. Правила формирования результата

1. **Регистр**: результат — `snake_case`, все буквы строчные (`lower_snake_case`).
2. **Единственное число**: каждое входящее слово переводится в единственном числе
   (`Договоры` → `contract`, а не `contracts`).
3. **Предлоги удаляются** из результата (например, `Для`, `С`, `В`, `На`, `По`, `Из`, `От`, `К` и т. п.).
4. **Общепринятые переводы** для учётных систем / ERP / бухгалтерского учёта
   (например, `Контрагент` → `partner`, `Договор` → `contract`, а не дословный `counterparty`/`agreement`).
5. Порядок слов в результате сохраняется в соответствии со смыслом исходного идентификатора
   (в примере `ДоговорыКонтрагентов` → `partner_contract`, т. е. перевод не дословно-пословный,
   а с учётом принятого в учётных системах термина «договор контрагента»).

## 3. Примеры (эталонные пары)

| Вход (1С CamelCase)      | Выход (snake_case)  | Статус |
|--------------------------|---------------------|--------|
| `ДоговорыКонтрагентов`   | `partner_contract`        | эталон, подтверждено |
| `ЗаказыПокупателей`      | `customer_order`          | эталон, подтверждено |
| `ТоварыНаСкладе`         | `warehouse_stock`         | эталон, подтверждено (промпт v2) |
| `СчетаНаОплату`          | `account_payment`         | получено от `gpt-oss-120b`, требует согласования |
| `ПоступлениеТоваровУслуг`| `receipt_product_service` | получено от `gpt-oss-120b`, требует согласования |

> Таблица будет пополняться по мере согласования правил и словаря.
> Все результаты получены на `gpt-oss-120b` через `POST /chat`.

## 4. Разбор входной строки

- Разбиение слитной строки на отдельные слова по границам `CamelCase`
  (заглавная буква начинает новое слово; учитывать аббревиатуры и цифры).
- Приведение каждого слова к начальной форме (единственное число, именительный падеж).
- Отбрасывание служебных слов (предлогов, союзов).
- Перевод каждого значимого слова с учётом предметной области (учётные системы).
- Склейка результата через `_`.

## 5. Принятые технические решения

1. **Источник перевода — LLM через API.** Собственный словарь терминов не является
   основным механизмом; терминология учётных систем задаётся промптом.
2. **Стек:** Python + FastAPI, HTTP-сервис. Конфигурация — YAML (`config/config.yaml`).
3. **Формат поставки:** веб-сервис с REST-эндпоинтом перевода (CLI/библиотека — при необходимости позже).
4. **Кеш обязателен:** повторные идентификаторы не должны приводить к повторным вызовам LLM.
   Бэкенд кеша (memory / file / redis) выбирается конфигурацией.
5. **Окружение:** локальное виртуальное окружение `.venv` в корне рабочей папки
   (`ПроектVSC/.venv`, Python 3.11), зависимости — из `requirements.txt`,
   секреты и локальные настройки — в `.env` (шаблон `.env.example`, `.env` исключён
   из репозитория через `.gitignore`).

## 10. API-слой (реализовано)

Файлы: [`api/schemas.py`](api/schemas.py), [`api/routes.py`](api/routes.py);
роутер подключается в [`main.py`](main.py).

### `POST /chat`

Запрос (JSON):

```json
{ "message": "ДоговорыКонтрагентов" }
```

Ответ `200`:

```json
{ "message": "ДоговорыКонтрагентов", "translated": "partner_contract" }
```

Правила валидации (`400 Bad Request` при нарушении):

| Правило                              | Тип ошибки Pydantic | Сообщение пользователю                      |
|--------------------------------------|---------------------|---------------------------------------------|
| `message` обязательно                | `missing`           | обязательное поле                           |
| `message` — строка                   | `string_type`       | должно быть строкой                         |
| пробелы по краям обрезаются (trim)   | —                   | —                                           |
| непустое после trim                  | `string_too_short`  | не должно быть пустым                       |
| длина ≤ 1000 символов                | `string_too_long`   | длина не должна превышать 1000 символов      |
| лишние поля запрещены                | `extra_forbidden`   | лишнее поле не допускается                  |
| тело — корректный JSON               | `json_invalid`      | тело запроса должно быть корректным JSON     |

Ответ `400` содержит `detail` с понятным текстом и `errors` — список `{field, message}`.

Проверено живым прогоном через `TestClient`: `200` — валидный запрос; `400` — пустая строка,
строка из пробелов, длина 1001, отсутствующее поле, лишнее поле, нестроковое значение,
битый JSON. Коды ошибок LLM — см. раздел 13.

Слой `api` не содержит бизнес-логики: роут вызывает
[`services.translator.translate_identifier()`](services/translator.py:15).

## 11. Бизнес-логика, промпты и конфигурация (реализовано)

### Конфигурация

Параметры корпоративного OpenAI-совместимого шлюза (заданы в `config/config.yaml`

| Параметр | Значение |
|---|---|
| `base_url` | `https://llm.enplus.group/v1` |

| `fallback_model` | `MiniMax-M2.7` (резервная) |

Совместимость проверена из окружения разработки: `GET /v1/models` без ключа → `401`
(`server: Angie/1.12.5`), `POST /v1/chat/completions` с заведомо неверным ключом → `401`
и `LLMError`. OpenAI Python SDK не используется — достаточно `httpx`, поэтому
фрагмент с `OpenAI(base_url=..., api_key=...)` переносится в настройки без изменения кода.

### Prompt builder — [`llm/prompts.py`](llm/prompts.py)

Системный промпт:

> Ты — полезный ассистент, профессиональный переводчик терминов учетных систем. Отвечай кратко и по существу.

Пользовательский запрос (`build_user_prompt(identifier)`) содержит идентификатор и требования:
`lower_snake_case`, только строчная латиница/цифры/`_`, единственное число, без предлогов
и союзов, терминология учётных систем, ответ без пояснений и markdown.
Отдельно требуется **переводить все смысловые компоненты** идентификатора — ничего не опускать
и не обобщать (именно из-за этого правила появился пример `ТоварыНаСкладе → warehouse_stock`
вместо прежнего `stock_item`).

Few-shot примеры в промпте (промпт v2):

```
ДоговорыКонтрагентов → partner_contract
ЗаказыПокупателей → customer_order
ТоварыНаСкладе → warehouse_stock
```

Проверка на реальной модели: все три эталона совпали; `СчетаНаОплату → account_payment`,
`ПоступлениеТоваровУслуг → receipt_product_service` (значения требуют согласования словаря).

### Клиент LLM — [`llm/client.py`](llm/client.py)

`complete(system_prompt, user_prompt, settings=None)` — синхронный вызов `chat/completions`
через `httpx` с таймаутом `llm.timeout_seconds`, ретраями `llm.max_retries`
(экспоненциальная пауза 1, 2, 4 … до 5 с) и fallback-моделью.

Алгоритм:

1. `model` — до `max_retries + 1` попыток;
2. если попытки исчерпаны и задан `fallback_model` — те же попытки на резервной модели
   (при необходимости через `fallback_base_url`);
3. если недоступны обе — типизированная `LLMError` со списком причин по каждой модели.

**Ретраи только для временных ошибок** (`LLMUnavailableError`): таймаут, сетевая ошибка,
HTTP 429 и 5xx. Ошибки 401/403 (`LLMConfigError`), прочие 4xx (`LLMRequestRejectedError`)
и невалидные ответы (`LLMResponseError`) не повторяются — сразу пробрасываются наверх.
Каждый внешний вызов обёрнут в `try/except` с преобразованием в типизированную ошибку.

Проверка на фейковом HTTP-клиенте (`tests/test_llm_client.py`): 500/429/таймаут → повтор,
403/400/невалидный JSON/пустой ответ → без повтора; при `max_retries=0` и падении основной
модели вызов уходит в `fallback_model`.

### Бизнес-логика — [`services/translator.py`](services/translator.py)

`translate_identifier(identifier, settings=None)` — единая функция, вызывающая компоненты:

```
build_user_prompt → llm.complete(SYSTEM_PROMPT, prompt) → normalize_snake_case → результат
```

Постобработка [`services/normalizer.py`](services/normalizer.py) выполняет:

- удаление markdown/кавычек и блоков рассуждений;
- `strip` по краям, обрезку лишних пробелов, табов и NBSP (`\u00a0`);
- переносы строк внутри «чистого» ответа (`partner\ncontract`) трактуются как разделитель,
  а при наличии посторонних символов/пояснений берётся первая содержательная строка;
- приведение к нижнему регистру, замена разделителей на `_`, схлопывание повторов `_`;
- удаление служебных слов (`of`, `for`, `in`, `on`, `to`, `with`, `from`, `by`, `and`, `or`,
  `the`, `a`, `an`);
- валидацию результата `is_valid_snake_case()` по шаблону `[a-z0-9]+(?:_[a-z0-9]+)*`
  (пустая строка, ведущие/замыкающие и двойные `_` недопустимы).

Пустой результат → `LLMError` «Модель вернула ответ без пригодного перевода»;
нарушение формата после нормализации → `LLMError` «некорректный формат (ожидался snake_case)».

Тесты постобработки: [`tests/test_normalizer.py`](tests/test_normalizer.py) — 32 кейса
(пробелы, табы, NBSP, переносы строк, markdown, reasoning-теги, пустые ответы, кириллица,
валидация snake_case, проверка `LLMError` при пустом ответе модели).

Отдельно отбрасываются блоки рассуждений reasoning-моделей
(`<think>…</think>`, `<thinking>…</thinking>`, `<reasoning>…</reasoning>`): резервная
`MiniMax-M2.7` возвращает цепочку размышлений прямо в `content`, и без очистки в результат
попадал мусор вида `think_1`. Если тег закрытия один (обрезанный reasoning) — берётся текст
после него; незакрытый блок отбрасывается.

Кеш пока не подключён (шаг 6): в `translate_identifier` оставлен TODO на проверку/сохранение.
Единственное число обеспечивается промптом; детерминированная морфологическая проверка
намеренно не делается, чтобы не портить термины (см. открытые вопросы).

## 12. Кеш переводов (реализовано)

Файлы: [`cache/ttl_cache.py`](cache/ttl_cache.py), [`cache/__init__.py`](cache/__init__.py).
Подключение — в [`services/translator.py`](services/translator.py:30).

### `TTLCache`

In-memory кеш «словарь + TTL» без внешних зависимостей:

- `get(key)` — значение или `None`, если записи нет либо истёк срок (просроченная запись удаляется);
- `set(key, value)` — запись с TTL от текущего момента;
- `delete`, `clear`, `purge_expired()`, `len()`, `in`;
- потокобезопасность через `threading.Lock` (FastAPI выполняет sync-хендлеры в пуле потоков);
- `max_size` — при переполнении вытесняется запись с ближайшим истечением срока;
- `clock` — подменяемый источник времени (в тестах — `FakeClock`), TTL проверяется детерминированно.

### Интеграция

`get_translation_cache(settings)` возвращает общий экземпляр `TTLCache[str, str]` либо `None`,
если `cache.enabled = false`. В `translate_identifier`:

1. ключ — идентификатор после `strip()`;
2. попадание → возврат значения без обращения к LLM;
3. промах → промпт → LLM → постобработка → `cache.set(key, result)`;
4. ошибки LLM **не** кешируются (следующий запрос снова идёт в модель).

Параметры в `config/config.yaml` / `.env`: `enabled`, `backend` (`memory` реализован;
`file`/`redis` пока не реализованы — используется memory с предупреждением в логе),
`ttl_seconds` (86400), `max_size` (10000).

Тесты: [`tests/test_cache.py`](tests/test_cache.py) — 11 кейсов (TTL, истечение, `purge_expired`,

## 13. Обработка ошибок (реализовано)

### Коды HTTP

| Код | Когда | Ответ |
|---|---|---|
| `200` | успешный перевод | `{message, translated}` |
| `400` | ошибка входных данных | `detail` + `errors[{field, message}]` |
| `502` | провайдер LLM отклонил запрос или вернул невалидный ответ | `detail` с причиной |
| `503` | LLM не настроена (нет ключа) или временно недоступна | `detail` с причиной |
| `500` | непредвиденная ошибка | «Внутренняя ошибка сервиса» (без внутренних деталей) |

### Типы ошибок — [`llm/errors.py`](llm/errors.py)

| Класс | Причина | HTTP | Ретрай |
|---|---|---|---|
| `LLMConfigError` | нет ключа, 401/403, неизвестная модель | 503 | нет |
| `LLMRequestRejectedError` | прочие 4xx от провайдера | 502 | нет |
| `LLMUnavailableError` | таймаут, сеть, HTTP 429, 5xx | 503 | да |
| `LLMResponseError` | не JSON, нет `choices/message/content`, пустой ответ | 502 | нет |

### Реализация

- Каждый внешний вызов обёрнут в `try/except`: `client.post` (таймаут/транспорт),
  разбор JSON, извлечение `content` — с преобразованием в типизированную ошибку.
- Обработчики в [`main.py`](main.py): `RequestValidationError` → `400`,
  `LLMConfigError`/`LLMUnavailableError` → `503`,
  `LLMResponseError`/`LLMRequestRejectedError`/`LLMError` → `502`,
  `Exception` → `500`.
- Логирование: `warning` для `400`, `error` для `502/503`, `exception` (со стеком) для `500`.
- Сообщения пользователю на русском и без раскрытия внутренних деталей/ключей.

Тесты: [`tests/test_api_errors.py`](tests/test_api_errors.py) — 15 кейсов (валидация, битый JSON,
маппинг всех типов ошибок LLM, 500, успешный сценарий, health);
[`tests/test_llm_client.py`](tests/test_llm_client.py) — 11 кейсов политики ретраев и fallback.

## 14. Логирование (реализовано)

Модуль — [`config/logging_config.py`](config/logging_config.py), настройки —
[`config/settings.py`](config/settings.py) (`LoggingSettings`), секция `logging`
в [`config/config.yaml`](config/config.yaml), переменные `LOG_*` в `.env`.
Инициализация выполняется при импорте [`main.py`](main.py).

### Вывод

- **Консоль** — `StreamHandler` (stdout);
- **Файл** — `RotatingFileHandler` UTF-8, `logs/transtalion.log`, ротация 5 МБ,
  5 архивных файлов; каталог создаётся автоматически;
- формат: `%(asctime)s | %(levelname)-8s | %(request_id)s | %(name)s | %(message)s`;
- приглушение логов `httpx` / `httpcore` / `urllib3` до `WARNING`;
- при `LOG_ENABLED=false` — `NullHandler` (вывод отключён полностью).

### request_id

Middleware в [`main.py`](main.py) генерирует 8-символьный `request_id`, кладёт его
в `contextvars` и возвращает в заголовке `X-Request-ID`. Фабрика записей лога и
`RequestIdFilter` добавляют поле в каждую запись, поэтому все сообщения одного
HTTP-запроса (API → services → LLM) связаны, включая записи из пула потоков FastAPI.

### Что логируется

| Этап | Уровень | Содержание |
|---|---|---|
| HTTP-запрос | `INFO` | `→ METHOD /path` (клиент), `← METHOD /path — статус за N с` |
| HTTP-ошибка | `WARNING` / `ERROR` / `exception` | `400` — предупреждение; `502/503` — ошибка; `500` — со стеком |
| API `/chat` | `INFO` | входное сообщение и длина, результат и время, ошибка перевода |
| Бизнес-логика | `INFO` | старт, попадание/промах кеша, промпт, ответ LLM, нормализация, запись в кеш |
| LLM-клиент | `INFO` / `WARNING` | модель, URL, temperature, попытка N/M, HTTP-статус, время, повторы, fallback |
| Ответ LLM (полный) | `DEBUG` | полный текст ответа в `llm.client`; в `services` — на `INFO` |

API-ключ в логи не пишется.

Тесты: [`tests/test_logging.py`](tests/test_logging.py) — 6 кейсов (файл + консоль,
отключение, `request_id` в записях, этапы перевода, ошибки LLM, заголовок `X-Request-ID`).
Всего в проекте `75 passed`.
